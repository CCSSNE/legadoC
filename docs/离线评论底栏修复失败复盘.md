# 离线评论底栏修复失败复盘

## 结论

本轮修复失败。

截至回滚时，离线评论页底部“发表评论”区域的真实渲染链路和根因没有被完整确认。此前提交的改动建立在局部现象和未经闭环验证的推断上，不应继续保留。

代码已恢复到本轮修改前的 `34680577` 状态。本文件只记录失败过程，不提供新的猜测性修复方案。

## 用户可见问题

离线评论快照中的底部发表评论区域表现异常：

1. 初始状态下底部垫高或底栏显示不完整。
2. 某些补偿版本在滑到页面底部时看似正常。
3. 页面向上滑动后，发表评论 DOM 会出现在页面中间，遮挡评论内容。
4. 在线评论网页不是问题对象，修复不得改变在线页面行为。

## 失败提交与思路

### `e7ac72c2`：回写系统安全区

思路：认为 Android WebView 中 `env(safe-area-inset-bottom)` 为 `0` 是根因，从原生 `WindowInsets` 回写 `--safe-b`。

失败原因：只证明了 CSS 环境变量为 `0`，没有证明它就是底栏只显示一部分的原因，也没有完成滑动全过程验证。

### `ccdd76f6`：清除 `FLAG_LAYOUT_NO_LIMITS`

思路：根据 DevTools 暴露的 WebView 高度和 `screenY` 推断 WebView 越出物理屏幕，因此修改整个 BottomSheet 窗口 flag。

失败原因：把不同坐标系的数据直接相减，并在没有证明窗口 flag 与离线问题存在因果关系时修改了在线、离线共用的窗口行为。该全局改动后来已撤销。

### `3d2a5b75`：按一次性裁切量抬升底栏

思路：用 `getLocationOnScreen()`、WebView 高度和屏幕高度算出裁切量，把 `bottomBar` 的 CSS `bottom` 和 `body.paddingBottom` 增加同样数值。

失败原因：把某一时刻、某一坐标系下的差值写成静态补偿。BottomSheet 或可视区域变化后补偿仍然存在，直接导致底栏悬浮到页面中间。

### `16cb5eef`：监听 BottomSheet 滑动更新补偿

思路：通过 `BottomSheetCallback.onSlide/onStateChanged` 动态重算上述补偿。

失败原因：没有先证明用户手势触发的是 BottomSheet 位移、WebView 内部滚动、VisualViewport 变化，还是三者组合；选错了观察信号。实机上 DOM 仍保留旧补偿。

### `ac791571`：每帧按绘制位置更新

思路：改用 `OnPreDrawListener`，在绘制前根据 WebView 屏幕坐标更新补偿。

失败原因：更新又被安排到下一帧，实机 DOM 中没有出现预期的 `bottom` 写入；没有先验证监听器、执行时序和页面身份状态就提交。

### `62d02d63`：把监听限制到离线快照

思路：恢复在线共用窗口行为，仅在 `displayingSnapshotHtml` 为真时安装监听。

结果：影响范围约束是必要的，但没有解决核心渲染问题。

### `d7b96471`：使用 `getGlobalVisibleRect()`

思路：改用 WebView 的全局可见矩形计算底部裁切量，并在当前绘制帧更新。

失败原因：仍然是在没有完整验证 View 层级、裁切父容器、WebView Surface、VisualViewport 和 CSS fixed 定位关系的情况下更换测量 API，继续属于猜测性修改。

## 已经确认的局部事实

以下事实只能作为后续调查材料，不能单独推出根因：

1. 离线快照 HTML 中保存过：
   - `<body style="padding-bottom: calc(80px + var(--safe-b));">`
   - `<div id="bottomBar" style="display: flex;">`
2. 在线页面通过脚本设置 `body.style.paddingBottom`；快照会移除原页面脚本。
3. 当前离线页面的 `bottomBar` 计算样式为 `position: fixed`。
4. 一次实机观测中：
   - `innerHeight = 872`
   - `visualViewport.height ≈ 683.05`
   - `visualViewport.offsetTop ≈ 189.33`
5. 向上滑动前后，曾观测到 `scrollY` 改变而 `bottomBar.getBoundingClientRect()` 保持不变。这只能说明当时 DOM 仍按 fixed 元素定位，不能证明屏幕合成后的最终位置正确。
6. DevTools 的页面描述、Android View 坐标、截图中的物理像素位置并未建立可靠的同一坐标系映射。
7. 直接通过 DevTools 临时修改 DOM 后再观察，会污染后续状态；这种观察不能代替从干净页面开始的复现闭环。

## 根本失败原因

1. 没有先建立稳定、可重复的最小复现步骤。
2. 没有完整追踪离线快照从抓取、序列化、读取、`loadDataWithBaseURL`、离线补充注入到最终 WebView 合成的全过程。
3. 没有证明具体是哪一层丢失或改变了垫高：快照 HTML、CSS cascade、DOM 注入、布局 viewport、visual viewport、BottomSheet 测量、父容器裁切或 Surface 合成。
4. 混用了 CSS px、Android dp、物理 px、窗口坐标和屏幕坐标。
5. 在只拿到局部数据时就将推断当成根因并修改代码。
6. 每次提交前没有完成“初始—上滑—中间—最底部—下滑返回”的动态验证闭环。
7. 失败后继续叠加补偿逻辑，使现象被前一版修改污染，进一步降低诊断可信度。

## 如果未来重新调查，必须先完成的闭环

在再次修改代码前，至少必须完成以下工作：

1. 从未注入任何临时 DOM 修改的干净离线快照开始复现。
2. 同时录制屏幕和采集每一帧关键状态：
   - BottomSheet 的 `top/bottom/translationY/state`
   - WebView 的 `top/bottom/height` 和全局可见矩形
   - `window.innerHeight`
   - `visualViewport.height/offsetTop/pageTop`
   - `scrollY/scrollHeight`
   - `bottomBar` 的 computed style 与 bounding rect
   - `body` 的 computed padding 和 bounding rect
3. 明确手势由哪个组件消费，并记录 NestedScrolling/BottomSheet 回调是否发生。
4. 在完全相同设备、相同 BottomSheet 状态下，对在线页和离线页采集同一组数据，找到第一个分叉点。
5. 沿快照链路逐步核对 HTML 是否发生改变，而不是只比较源文件与最终 DOM。
6. 找到第一个确定的错误层后，只在离线路径做最小修复。
7. 修复后必须验证：
   - 初始状态底栏完整且位于可视底部
   - 连续上滑时底栏不随正文漂移、不悬浮到中间
   - 滑到最底部时最后一条评论不被遮挡
   - 下滑返回后位置仍正确
   - BottomSheet 展开、折叠转换均正确
   - 在线评论页的 DOM、CSS、窗口配置和交互完全不变

在上述证据链完成前，不应再提交任何 padding、inset、窗口 flag、固定偏移或动态补偿方案。
