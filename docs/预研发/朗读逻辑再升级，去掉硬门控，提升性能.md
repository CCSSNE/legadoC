

## 老版本现状

**老版其实是“粗暴但干净”的架构隔离**。

核心就是两条完全分开的路：

**非 WAV**
 → 直接 `speak(QUEUE_FLUSH)`
 → 不查缓存
 → 有缓存也当不存在
 → 不碰实时缓存那套状态机。

**WAV**
 → 才进入“生成文件 / 查缓存 / 播文件 / 实时缓存 / 整章缓存”这一整套体系。

所以这个门禁真正解决的不是一个 UI 限制，而是：

**它直接砍掉了一大批交叉状态。**

代价当然也明显：

> 明明磁盘上已经有整章缓存，WAV 没开也不给你用。但是开了呢，打到缓存外又会小卡一下，但是可以通过按段朗读来缓解。
>
> 在意流畅度的话，就直接不开 WAV 不就行了，只是可能不是那么省电。



### 老版本其实更符合实际，新版本强行融合有些无病呻吟。

本地 TTS 引擎主要分两类：

1. 支持流式

只要 RTF < 1，生成速度跟得上播放速度，实时朗读就能保持流畅。这类引擎通常不需要实时缓存或整章缓存。

如果用户想播放已生成的音频、减少重复合成或省电，可以主动开启 WAV 模式。缓存外内容的等待问题，则可通过关闭分页切段、改用按段朗读等现有配置处理，无需打通两套播放体系。

2. 不支持流式

这类引擎实时朗读必然存在等待，实时缓存才有价值：提前生成后续 WAV，减少播放间断。

由于它本身不支持流式，开启 WAV 模式没有额外损失，因此合理组合就是：

WAV 模式 + 实时缓存

所以，老版本的门禁虽然严格，但符合实际：

- 流式引擎：实时朗读，不进入 WAV 缓存体系；
- 非流式引擎：开启 WAV 和实时缓存；
- 用户明确需要缓存音频：主动开启 WAV。

新版融合的主要收益，只是减少用户手动切换一次开关。但它没有真正识别引擎是否支持流式，反而把原本隔离的两套体系连接起来，引入缓存命中、在途等待、打断、暂停和回调等复杂状态。

如果要做自动化，正确方向应是根据引擎能力、RTF 和首包延迟自动选择播放模式，而不是在现有体系上强行融合。



### 3 个 UI 开关

**1. 实时缓存**

- 开：朗读当前句时，后台预生成后面 N 段 WAV。
- 关：不做跟随朗读的预生成。
- 不再强制依赖 WAV 模式，原来的门禁考虑取消。

**2. 等待生成**
主要处理：**当前要读的句子恰好“正在生成 WAV”时怎么办。**

- 开：等它生成完 → 播 WAV。
- 关：不等 → 直接发实时 `speak()`。
- 原来正在合成的 WAV **不取消、不丢弃**，回来后正常落库。
- 如果引擎本身串行，必须等 WAV 合成结束才处理实时 speak，这是引擎调度问题，接受。

**3. 边读边存**
完全独立，不参与“这一句怎么播放”的判断。

- 开：正常朗读过程中产生的 WAV 也长期入库。
- 关：普通读过的内容不因为“读过”而入库。
- 实时缓存、整章缓存本来该落库的仍然照常落库。

------

### 当前句决策优先级

**第一优先级：缓存命中**

- 不管 WAV 开没开。
- 不管实时缓存开没开。
- **只要命中有效 WAV → 直接播文件。**
- 这是最高优先级，不再讨论。

**第二种：当前句正在合成**

- `等待生成=开` → 等 WAV → 播文件。
- `等待生成=关` → 直接实时 speak。
- 原 WAV 继续自己的任务；回来以后该落库就落库。

**第三种：当前句完全缺失**

- 缓存没有。
- 也没有正在合成。
- **直接实时 speak，不为了当前句新发 WAV 合成然后傻等。**
- 这是“等待生成开启后仍然能够零等待起步”的核心。

------

### 实时缓存的真正作用

当前句怎么播和后文预取要分开。

例如刚开始朗读第一句：

- 第一段完全缺失 → 直接实时 speak。
- 后面的第 2、3、4……段由实时缓存用 WAV 方式后台生成。

所以：

**实时播放解决“现在”。**
**WAV 预取解决“以后”。**

用户跳转时，如果正好跳到后台正在生成的某句，才触发“等待生成”开关。

------

### WAV 正常朗读

如果本身开启 WAV 朗读：

- 当前句正常走 WAV 合成/播放体系。
- `边读边存=开` → 读过的 WAV 转成正式缓存。
- `边读边存=关` → 普通朗读临时 WAV 用完可以清理。
- 如果这个 WAV 本身属于实时缓存/整章缓存任务，则仍按任务本身规则入库。

------

### 单 TTS 实例

明确不搞双实例、双连接之类的补丁。

原则：

- **单 TextToSpeech 实例。**
- Android/TTS 引擎做不到的就明确暴露。
- 有异常直接日志/报错。
- 不搞“失败了偷偷切另一套逻辑”的静默兜底。

------

### 打断问题(当时以为没有打断命令 实际后面发现有)

需要正式研发时再次实测 Android `TextToSpeech`：

- `QUEUE_FLUSH`
- `stop()`
- `synthesizeToFile()`
- 同实例正在进行的合成任务

之间到底如何相互影响。

这块不能靠想当然。

尤其要确认：

**实时 speak 是否必然会中断正在进行的 WAV 合成。**

如果系统/具体引擎事实上不能独立打断某个任务，那么方案就按：

> 不管旧 WAV，让它生成完；实时请求照发；回来正常落库。

------

### 暂停

目标语义：

**暂停当前朗读 ≠ 暂停后台预生成。**

后台预取本来有最大段数限制，所以暂停后：

- 已排的预生成任务继续生成。
- 不应该主动清掉缓存队列。

但如果 Android 单实例 API 导致“停止实时播报”必然同时杀掉合成任务，这属于平台边界，实施前必须实测并在日志中明确，而不是假装没有这个问题。

------

### 等待生成的超时

不能无限死等在途 WAV。

需要：

- 在途等待有 watchdog。
- 超时必须明确记日志。
- 后续是“转实时播放”还是“直接报错”，实施阶段再定。

原则不变：

**不能静默卡住。**

------

### 句内进度

播 WAV 时优先使用真实文件播放进度。

如果拿不到精确值，回退顺序：

**真实 WAV 时长/播放位置**
→ **按当前文本字数预测**
→ **根据前一句实际朗读速度预测**

不能因为这套缓存改造把原来的句内进度搞废。

------

### 日志必须成为方案的一部分

不是最后顺手加日志。

朗读日志必须直接能看到每一句为什么这样决策，例如：

- `CACHE_HIT -> PLAY_WAV`
- `IN_FLIGHT + WAIT_ON -> WAIT_WAV`
- `IN_FLIGHT + WAIT_OFF -> LIVE_SPEAK`
- `MISSING -> LIVE_SPEAK`
- `PREFETCH -> SYNTHESIZE`
- `WAV_RETURNED -> COMMIT_CACHE`
- `READ_AND_SAVE -> COMMIT`
- `WAIT_TIMEOUT`
- `TTS_STOP / ON_STOP / SYNTH_CANCELLED`

以后出 bug，可以直接沿日志还原整个状态变化。

### 最终破防点

**显式打断**：`TextToSpeech.stop()`

**隐式打断**：`speak(text, QUEUE_FLUSH, …)`

- 有了打断指令（且打断可能非瞬时、是否可取消不透明）之后，“命中正在合成的一句 → 直接打断 → 走它”看似可行，但打断的时效性/可取消性全是未知数，迷雾太多；
- 与其在单实例+打断语义的泥潭里精细手术、堆断点日志和看门狗补救，不如认清这条路代价高、风险不透明；
- 回到**老门禁**，不碰它，最稳。
