# 下载/缓存架构标准

本文是阅读 C 下载/缓存域的唯一目标架构契约和设计标准。源码应向本文收敛；本文不为临时实现妥协，也不把即时阅读加载误纳入后台缓存任务域。后续修改以本文为准，不以历史迁移过程、旧提交说明、临时排障记录或某一次版本验证结果为准。

本文同时约束：任务所有权、业务状态、生命周期、结果、运行态进度、通知投影、生命周期日志、性能诊断、并发流水线、内存预算、暂停/恢复/取消和进程恢复。

---

## 1. 范围与总原则

缓存域只包含：

```text
TEXT + BODY          正文
TEXT + REVIEW        评论
AUDIO + MEDIA        音频
AUDIO + REVIEW       音频书原生评论
VIDEO + MEDIA        视频
```

导出是独立领域，不进入 `CacheCoordinator`。

统一的是任务所有权、业务状态、命令、终态、进度契约、通知、生命周期日志、性能诊断和恢复；正文、评论、音频、视频仍保留各自合理的底层执行器。

唯一数据流：

```text
入口
  │
  ▼
CacheCoordinator          唯一任务 Owner
  │
  ▼
CacheTaskStore            唯一业务状态来源
  │
  ▼
Worker / Adapter          执行翻译层
  │
  ▼
底层执行器
  │
  ├── lease + progress
  ├── lease + unit update
  └── lease + finish
          │
          ▼
CacheTaskStore
  │
  ├── UI
  ├── CacheNotificationBridge
  └── AppLog / cache_perf
```

完整结构：

## 2. 职责边界

### 2.1 `CacheCoordinator`：唯一任务 Owner

负责：

- 接收和校验 `CacheRequest`。
- 创建 session / task。
- 分派 worker。
- 处理暂停、恢复、取消。
- 建立 TEXT/BODY、AUDIO/MEDIA 到同领域 REVIEW 的章节依赖。
- 接收 reader 刷新意图。
- 协调 reader REVIEW 与已有 REVIEW task 的复用/冲突。
- Store 接受终态后触发通知投影。

Coordinator 不执行网络、WebView、ExoPlayer、正文解析、HTML 序列化或文件写入。

### 2.2 `CacheTaskStore`：唯一业务状态来源

Store 统一拥有并发布两类状态：

```text
可恢复业务状态                         高频运行态
┌────────────────────┐               ┌──────────────────────┐
│ CacheSnapshot      │               │ CacheProgressState   │
│ Session / Task     │               │ task / unit progress │
│ Unit / Lifecycle   │               │ display selection    │
│ Result / Generation│               └──────────┬───────────┘
└─────────┬──────────┘                          │
          └──────────────────┬──────────────────┘
                             ▼
                       CacheTaskStore
```

规则：

- session/task/unit/lifecycle/result/generation 属于可恢复业务状态，进入 `CacheSnapshot` 并按现有持久化策略保存。
- progress 是 Store 拥有的高频运行态，不要求写进持久化 `CacheSnapshot`；可以由 Store 使用独立内存结构/Flow 发布。
- progress 仍必须经过 lease/generation 校验，Notification/UI 不能直接从 executor 的局部状态取值。
- 新 generation 接管时清除旧 progress，重新建立当前进度；不能恢复旧传输百分比。
- 所有异步业务回报和 progress 回报都必须经过 Store 的 lease 校验。

执行器可以保留内部队列、Future、WebView、播放器、网络请求和局部计数作为实现细节；这些局部状态可以用于调度、暂停恢复和底层执行，但不能成为 Notification/UI 的权威进度来源，也不能替代 Store 中经 lease 校验的统一 progress。

### 2.3 Worker / Adapter：执行翻译层

```text
TextBodyWorkerAdapter -> CacheBook / CacheBookService
ReviewWorkerAdapter   -> ReviewSnapshotManager / ReviewCacheService
MediaWorkerAdapter    -> 媒体执行宿主 / 媒体执行器
```

Adapter 只负责：

```text
Coordinator 命令
   ↓
执行器调用
   ↓
progress / unit / finish
   ↓ + lease
CacheTaskStore
```

Adapter 不创建第二个 session，不推断全局终态，不直接更新通知。

### 2.4 Android Service：执行宿主

`CacheBookService`、`ReviewCacheService` 只承载前台服务和长生命周期执行。

Service 可以：

- `startForeground()`。
- 承载 adapter / executor 生命周期。
- 宿主销毁时把恢复或异常交回 dispatcher / Coordinator。

Service 不可以：

- 拥有任务。
- 决定业务终态。
- 直接写 Store。
- 控制另一个 Service。
- 构造最终通知。

是否合并 Service 不是本标准的目标。

## 3. 数据模型

### 3.1 `CacheRequest`

核心字段：

```text
source = CACHE_ACTIVITY | CACHE_MANAGE | READER | AUTO_PRECACHE | SYSTEM
kind   = TEXT | AUDIO | VIDEO
phase  = BODY | REVIEW | MEDIA
bookUrl
bookName
units
reviewEnabled
```

合法组合：

```text
TEXT  + BODY
TEXT  + REVIEW
AUDIO + MEDIA
AUDIO + REVIEW
VIDEO + MEDIA
```

Coordinator 必须拒绝非法组合，例如媒体使用 BODY、视频使用 REVIEW、未授权入口绕过依赖直接提交 REVIEW。

### 3.2 Session / Task / Unit

```text
CacheSession
   │
   ├── TEXT / BODY 或 AUDIO / MEDIA task
   │      └── chapter units
   │
   └── 同 kind / REVIEW task
          ├── 主产物成功章节对应的 review unit
          └── ...
```

规则：

- 正文是 `TEXT + BODY` task。
- 正文产生的评论是同一 session 内的 `TEXT + REVIEW` task。
- 音频和视频使用 `MEDIA` phase，各自按 task 管理；音频书原生评论是同一 session 内的 `AUDIO + REVIEW` task。
- REVIEW task 只包含同 kind 主产物成功且需要评论的章节。
- 音频书从原始 `lyric` 解析原生评论；配对文本书融合进音频页的评论仍归原文字书 `TEXT + REVIEW`，音频 overlay 只是展示投影，不得重复缓存。
- 一个 task 的所有 unit 必须属于同一本书。

### 3.3 Unit 依赖

```text
CacheUnitKey(bookUrl, chapterIndex)
       │
       ├── primary unit（TEXT/BODY 或 AUDIO/MEDIA）
       │      ├── SUCCEEDED ─────► 同 kind REVIEW unit 可创建
       │      └── FAILED ─────────► 只阻断本章 REVIEW
       │
       └── REVIEW unit
              └── FAILED 不污染主产物成功结果
```

Unit 状态：

```text
PENDING
RUNNING
SUCCEEDED
FAILED
REVIEW_ELIGIBLE
REVIEW_BLOCKED
NOT_APPLICABLE
CANCELLED
```

规则：

- 主产物失败只阻断同一章节 REVIEW，不阻断其它章节。
- REVIEW 失败不改变该章节已经成功的 BODY/MEDIA。
- 主产物进入终态后，Coordinator 必须先补建可用 REVIEW task，再投影 Session 终态。
- reader 对同书同章节的活动 REVIEW 请求必须复用现有 task，不能形成相互 ownership 冲突的重复 task。
- `REVIEW_ELIGIBLE`、`REVIEW_BLOCKED`、`NOT_APPLICABLE` 是 unit 层依赖/兼容状态，不是 task/session 生命周期；没有明确数据迁移前不得擅自删除。
- `RUNNING` 表示该 unit 已被当前 generation 的 worker 接管，不等价于“此刻正在占用网络/CPU”。真正的当前展示章节和章内进度由 Progress Contract 表达；不得通过猜测哪个 `RUNNING` unit 来推断当前章节。
- 是否把 unit 延迟到真正取出执行时才置为 `RUNNING` 属于独立的状态语义/性能优化议题，不是 Progress Contract 的前置条件；不得为了实现通知进度顺带修改该语义。

### 3.4 Artifact Ownership / Completeness Contract

`kind + phase` 同时决定持久化产物的所有者和完成条件：

| Artifact | 持久化产物 | Unit `SUCCEEDED` 的必要条件 |
|---|---|---|
| `TEXT + BODY` | 正文缓存 | 本章正文产物完整可读 |
| `TEXT + REVIEW` | 文字书评论快照、状态和资源 | 所有目标快照处理完成、每张快照的本地资源闭包完整且失败数为 0 |
| `AUDIO + MEDIA` | `resourceUrl`、原始 `lyric`、远程媒体缓存或导入音频实体 | 媒体可用且原始 `lyric` 非空 |
| `AUDIO + REVIEW` | 音频书原生评论快照、状态和资源 | 所有目标快照处理完成、每张快照的本地资源闭包完整且失败数为 0 |
| `VIDEO + MEDIA` | `resourceUrl`、媒体缓存及所需持久化清单 | 媒体产物完整可用 |

硬约束：

- 不同领域的产物不得互相充当完成依据；音频不得用 BODY cache 证明完整，融合 overlay 不得冒充音频书原生 REVIEW。
- Manifest 是持久化索引和恢复材料，不是完成事实源；Manifest、缓存管理、恢复和导出必须复用对应领域唯一的纯完整性判断入口。
- 不建立万能 `CompletenessRegistry`，也不建立第二 Store。Task 状态只归 `CacheTaskStore`；文件完整性由各领域纯 checker 派生。
- 导入音频的媒体可用性来自持久化音频实体，不要求 ExoPlayer cache；远程音频才校验其媒体缓存。
- VIDEO/MEDIA 解析使用 `needSave=false`，不得读写 BODY cache；内联 M3U8/MPD 必须进入视频媒体持久目录后再写入 `resourceUrl`，不得引用临时 cache 文件。
- REVIEW 的 `processedSnapshots == totalSnapshots` 只表示执行收敛；只有 `failedSnapshots == 0` 才允许 Unit `SUCCEEDED`，否则 Unit 必须 `FAILED`。
- 导出继续独立于 `CacheCoordinator`；音频导出格式只允许音频、原始 `lyric` 和所有章节绑定 sidecar 保持同一章节集合的 `TXT-ZIP`。“整体”表示包内单章产物不可拆分，不表示整本目录必须全部下载。
- 音频导出先计算唯一选择集合 `S = 非卷章节中 AudioOfflineState.isComplete 的章节`。目录全集只是候选集，不是导出前置条件；`S` 为空才拒绝导出，`S` 外未下载或半完成章节必须忽略，不得阻断导出。
- Manifest、TXT、媒体文件及所有章节绑定 sidecar（评论、配图、书签等）必须复用同一个 `S`；稀疏源章节进入归档时，sidecar 章节索引必须按 `S` 的归档顺序重编号。选入 `S` 后若打包时发现媒体、原始 `lyric` 或所选资源缺失，必须直接报错；不得解析书源、提交缓存任务或在导出线程内隐式下载/补缓存。书名、作者、简介、替换规则等整本级产物不受 `S` 过滤。
- 导出文件发布必须使用“同目录 staging 完整写入并校验后再替换正式文件”的提交语义；生成或写入失败时旧归档必须保持可用，不得在新归档成功前删除或截断旧归档。
- 音频归档导入以 Manifest 的章节顺序和源章节 URL 为身份事实源，直接恢复音频章节实体与章节所有的评论 sidecar；TXT 只是包内可读文本，不得重新分章后用稀疏原索引或标题近似匹配来决定音频章节归属。

### 3.5 Lease

```text
CacheWorkerLease
  sessionId
  taskId
  generation
```

新 task 从 `generation=0` 开始；每次 acquire/reclaim、暂停后恢复、进程恢复或宿主重新接管都取得新 generation。

```text
旧 callback
    │
    ▼
lease.generation != Store.generation
    │
    ├── 拒绝状态写入
    └── STALE_UPDATE_DROPPED
```

旧 lease 不能静默写入新 task。

### 3.6 Progress Runtime State

进度是正式架构运行态，但不要求塞进持久化 `CacheSnapshot`。Store 可以维护独立、非持久化的 progress map/Flow。

单条进度：

```text
CacheProgressState
  sessionId
  taskId
  generation
  unitKey?
  mode                   CHAPTERS | BYTES | SNAPSHOTS | INDETERMINATE
  current
  total?
  updatedAt
```

并发 REVIEW 不能只有一个会被反复覆盖的 task-level current progress。Store 必须允许同一 task 同时存在多个 unit progress：

```text
ProgressKey = sessionId + taskId + generation + unitKey?

CacheTaskStore
   │
   ├── task progress              BODY 的总体章节进度可由 Unit 直接派生
   │
   └── unitProgress[]
          ├── chapter 2 -> SNAPSHOTS 2/60
          ├── chapter 3 -> SNAPSHOTS 8/40
          └── chapter 4 -> SNAPSHOTS 1/12
```

进度回报路径：

```text
executor
   │  局部 bytes / snapshots / stage counters
   ▼
adapter / progress callback
   │  progress + lease
   ▼
CacheTaskStore
   │  generation 校验
   ├───────────────┬────────────────┐
   ▼               ▼                ▼
Notification       UI          diagnostics
```

允许 executor 内部保留局部计数用于执行；禁止 Notification/UI 直接读取这些局部计数作为权威进度。

禁止：

```text
AudioCacheTaskManager._states ───────────────► Notification
ReviewSnapshotManager.notificationProgress ─► Notification
ExoPlayer progress callback ─────────────────► Notification
```

正确做法是把这些局部信息经 adapter/progress callback 转成带 lease 的 Store progress。

## 4. 生命周期和结果

### 4.1 生命周期

```text
QUEUED
  │
  ▼
RUNNING ───────────────► COMPLETED
  │                         │
  │                         └── result = SUCCEEDED | PARTIAL | FAILED
  │
  ├──► PAUSING ─► PAUSED ─► RUNNING
  │
  └──► CANCELLING ────────► CANCELLED

QUEUED ─► CANCELLING ─────► CANCELLED
PAUSED ─► CANCELLING ─────► CANCELLED

INTERRUPTED ─► RUNNING
      └──────► CANCELLING / CANCELLED
```

终态：

```text
COMPLETED
FAILED
CANCELLED
```

`PAUSING`、`CANCELLING` 是过渡态；`INTERRUPTED` 是进程恢复时等待重新接管的状态。

### 4.2 Result 与 Lifecycle 分离

结果：

```text
SUCCEEDED
PARTIAL
FAILED
CANCELLED
```

| 实际情况 | lifecycle | result |
| --- | --- | --- |
| 所有 unit 成功 | `COMPLETED` | `SUCCEEDED` |
| unit 全部执行，部分成功、部分失败 | `COMPLETED` | `PARTIAL` |
| unit 全部执行，但全部失败 | `COMPLETED` | `FAILED` |
| 异常结束且仍有 unfinished unit | `FAILED` | `FAILED` 或按已完成 unit 汇总为 `PARTIAL` |
| 取消确认完成 | `CANCELLED` | `CANCELLED` |

规则：

- `PARTIAL` 不是生命周期。
- 正常执行完但业务结果全失败必须是 `COMPLETED + FAILED`。
- 只有仍有 unfinished unit 的异常收尾才使用 `lifecycle=FAILED`。
- Store 不接受带 unfinished unit 的成功收尾。
- 异常收尾必须把未完成 unit 明确收敛为失败或取消状态。
- `finishTask()` 不接受 `CANCELLED`；取消必须经过 `beginCancel()` 和 `confirmCancelled()`。
- 终态写入后，旧 lease 和后续 worker 回报一律拒绝。

Session 状态由 Task 汇总：

```text
存在活动 task      -> session 非终态
全部取消           -> CANCELLED
成功 + 失败/取消   -> PARTIAL
全部成功           -> SUCCEEDED
全部执行完且全失败 -> FAILED
```

## 5. 入口和命令

以下入口只能调用 `CacheCoordinator` 并观察 Store 派生状态：

| 入口 | 职责 |
| --- | --- |
| `CacheActivity` | 正文提交、状态观察、暂停/恢复/取消 |
| `CacheManageActivity/ViewModel` | 正文/媒体提交、状态观察、任务命令 |
| 阅读页 | 即时阅读加载不属于 Cache Task；若产生章节评论刷新意图则提交 Coordinator |
| `MainViewModel` | 自动预缓存提交 |
| 通知 action receiver | 将通知动作转为 Coordinator 命令 |
| 音频/视频页面 | 显式下载只提交 Coordinator；按书籍类型分派 BODY 或 MEDIA，并观察 Store 派生状态 |

公共 UI 端口：

```text
snapshot
submit
pause
resume
cancel
```

范围边界：

```text
阅读当前/前后章，为了立即渲染而按需抓正文
ReadBook -> CacheBook.downloadAwait
        = 阅读加载域，不创建 Cache Task，不进入离线缓存通知/暂停/恢复

可暂停、可恢复、可通知的离线缓存与后台长任务
        = 缓存域，必须进入 CacheCoordinator

ReadBook 的即时正文加载与普通前后章预加载
        = 阅读加载域，允许直接调用 CacheBook，不创建 Cache Task

当 `syncCacheReview && autoDownloadReview` 开启时，阅读页的自动评论预缓存
        = 由 `ReadBook.scheduleAutomaticReviewDownload()` 提交 CacheCoordinator，先完成 BODY/MEDIA，再追加 REVIEW

阅读页显式刷新正文时产生的“缓存该章评论”意图
        = 先由 `CacheCoordinator.markReviewRefresh()` 持久化为无 TTL 的强制刷新标记；下一次满足 REVIEW 前置产物完整、且有自动/显式 REVIEW 调度时，由 Coordinator 消费该标记并创建/复用 REVIEW task。标记本身不伪造一个尚未满足前置条件的 task。
```

“写入了正文缓存文件”本身不等于“属于 CacheCoordinator 缓存任务”；判断标准是它是否是可管理的后台 Cache Task。

UI / ViewModel 在缓存域内不得直接调用：

```text
CacheBookService
ReviewCacheService
CacheBook / CacheBookModel
ReviewSnapshotManager
媒体底层 Manager
内部 CacheWorkerPort
```

## 6. 进度、通知和日志

### 6.1 Progress Contract

总体章节进度和主进度条是两个不同概念，不得混用。

```text
当前缓存进度
━━━━━━━━━━━━━━━━━━━━━━━━━━

缓存正文时
主进度条 = 已完成章节数 / 总章节数
下方文字：
2/5章

缓存视频时
主进度条 = 当前章节已下载大小 / 当前章节总大小
下方文字：
8.4MB / 60MB  2/5章

缓存音频时
主进度条 = 当前章节已下载大小 / 当前章节总大小
下方文字：
8.4MB / 15.2MB  2/5章

缓存评论时
主进度条 = 当前章节已处理快照数 / 当前章节总快照数
下方文字：
快照：2/60  失败：0  2/5章
```

固定语义：

- BODY：主进度条表示整个 task 的章节完成比例。
- AUDIO / VIDEO：主进度条只表示当前章节的字节进度。
- REVIEW：主进度条只表示当前章节的快照处理比例；`已处理 = 成功 + 失败`。
- `x/y章` 始终表示整个 task 的章节完成数 / 总章节数。
- REVIEW 的 `快照：x/y` 只表示当前章节内部，不得与总章节数混算；`失败：n` 也是当前章节的失败数，不能累计其它章节。
- `total` 尚未知时使用 `INDETERMINATE`，不得伪造 `0/100`。
- 多章节并发时必须选定一个明确且稳定的 `displayUnit`；不同章节的 bytes / snapshots 不得混进同一条主进度条，也不得因为另一个 unit 刚更新就自动抢占显示。
- `x/y章` 中的 `x` 永远是 `SUCCEEDED unit count`，不是当前章节序号。当前正在第几章如需展示，必须使用独立字段/文案，不能冒充总体完成数。

### 6.2 Notification Projection

`CacheNotificationBridge` 是唯一缓存通知构造/更新路径：

```text
Store snapshot / progress
          │
          ▼
CacheNotificationBridge
          │
          ▼
Android Notification
```

通知必须表达：

```text
当前缓存类型
当前章节 / displayUnit
主进度条
当前章节内部进度
总体章节进度 x/y章
```

示例：

```text
Offline cache
我在修仙世界开农场
评论缓存中
快照：2/60  2/5章
[████████░░░░░░░░░░░░]
```

规则：

- progress 从 Store 统一状态生成。
- action 只发送 Coordinator 命令。
- Store 接受终态后才发送终态通知。
- 终态结果优先使用 session 汇总结果。
- foreground host 只使用 Bridge 提供的基础通知。
- worker、executor、Service 不得直接形成第二通知源。
- 通知不是状态源；通知丢失、延迟或进程重启都不能改变 Store 事实。
- BODY/MEDIA 已完成但同 session 的 REVIEW 仍运行时，只能显示“主下载已完成 / 评论缓存中”，不能把整个 session 表述为已完成。
- 多 task 同时活动时，主进度条只能绑定一个稳定、可解释、可测试的 `displayTask/displayUnit`；其它活动 task 只能摘要展示，不能混合分子分母。
- `displayTask` / `displayUnit` 的选择不得使用“谁最后一次 progress 更新就显示谁”的策略，因为 MEDIA bytes 与 REVIEW snapshots 会造成通知来回跳。
- display selection 属于 Store/Coordinator 管理的瞬时投影状态；可以保存 `displayTaskId/displayUnitKey`，也可以使用等价且稳定、可测试的纯函数选择规则，但不得由 executor 的“最近更新时间”直接决定。progress tick 本身不得切换 displayTask。
- 一个 displayTask 选定后，在它终态、暂停/取消或明确的用户焦点切换之前保持稳定；displayUnit 也应保持到该 unit 完成/失效后再选择下一项。

### 6.3 Lifecycle / Business Log

统一进入 `AppLogCacheLogSink`：

```text
SESSION_CREATED / SESSION_RECOVERED
TASK_QUEUED / TASK_STARTED / TASK_RECLAIMED
TASK_PAUSING / TASK_PAUSED / TASK_RESUMED
TASK_CANCELLING / TASK_CANCELLED / TASK_FINISHED
UNIT_UPDATED / UNIT_FAILED / UNIT_PROGRESS_SUMMARY
STALE_UPDATE_DROPPED
PERSISTENCE_LOAD_FAILED / PERSISTENCE_SAVE_FAILED
WORKER_DISPATCH_FAILED / REQUEST_ACCEPTED
```

规则：

- 日志必须携带可用的 session / task 标识和原因。
- `UNIT_UPDATED` 属于高频日志，可以采样并在 task 结束时输出汇总。
- `UNIT_FAILED`、终态、异常、`STALE_UPDATE_DROPPED` 不得被采样隐藏。
- Store 的真实状态更新不能因为日志采样而丢失。
- 异常不能用静默 catch、默认成功或无依据回退隐藏。

### 6.4 Performance Diagnostics

生命周期日志回答“谁拥有任务、状态怎么变”；性能日志回答“执行器在哪个阶段变慢、变大、占多少资源”。两者不能互相替代。

统一字段：

```text
cache_perf
  domain=STORE|BODY|REVIEW|MEDIA
  event=...
  session=...
  task=...
  generation=...
  chapter=...
  elapsedMs=...
  active=...
  heapUsedBytes=...
  heapMaxBytes=...
  heapPercent=...
  inputChars=...
  outputChars=...
  inputBytes=...
  outputBytes=...
  resources=...
```

重操作边界：

```text
START
  │
  ├── stage mark...
  │
  └── DONE | FAILED | CANCELLED
```

REVIEW 典型事件：

```text
CAPTURE_START
PAGE_EXECUTION_START / DONE / FAILED
HEAVY_STAGE_WAIT_START / DONE / FAILED
HEAVY_STAGE_ACQUIRED
HEAVY_STAGE_WORK_START / DONE / FAILED
RESOURCE_LIST_READY
RESOURCE_INLINE_READY（当前日志名；语义为资源库写入与 DOM 引用替换完成）
WEBVIEW_HTML_READY
SANITIZE_START / DONE / FAILED
SNAPSHOT_WRITE_START / DONE / FAILED
CAPTURE_DONE / FAILED
```

日志规则：

- 关键重操作 START 必须可见，不能因为 sampling 导致永久卡死时完全没有入口日志。
- 慢操作阈值按该 operation / stage 自己的耗时计算，不能用整个 CAPTURE 的累计时间冒充某个 stage 的耗时。
- 大对象、高 heap、慢操作、失败必须强制进入 AppLog。
- 高频成功操作可以采样。
- 记录“大小、数量、耗时、并发、水位”，不记录完整 HTML、正文、音频、视频等大 payload。
- 诊断系统本身不能成为新的 I/O 或内存瓶颈。

## 7. 持久化和进程恢复

`CacheTaskStore` 持久化可恢复的 `CacheSnapshot`。

恢复流程：

```text
进程启动
   │
   ▼
读取 CacheSnapshot
   │
   ├── 失败 -> PERSISTENCE_LOAD_FAILED
   │
   ▼
状态收敛
   │
   ├── RUNNING    -> INTERRUPTED
   ├── PAUSING    -> PAUSED
   └── CANCELLING -> CANCELLED
   │
   ▼
dispatcher 扫描 QUEUED / INTERRUPTED
   │
   ▼
获取新 generation lease
   │
   ▼
Adapter / Executor 重新接管
```

规则：

- Service 不能自行读快照并绕过 Store 重启任务。
- 恢复不能复用旧 lease。
- 旧瞬时 progress 不作为恢复事实；新 generation 重新建立当前章节内部进度。
- 持久化读写失败必须进入日志，不得静默忽略。

## 8. 并发、流水线、内存预算和隔离

并发是执行器内部运行策略，不改变 Owner、Store 和 lease 边界。

### 8.1 REVIEW：多流水线并行，重内存阶段独立限流

```text
ReviewCacheService：章节消费者 = 1（固定）
│
└─ 当前章节的 ReviewSnapshotManager
   │
   ├─ 全局 Capture Pipeline = 2（固定）
   │  ├─ A：resolve(20s) → page/load/expand(自己的 60s) ─┐
   │  └─ B：resolve(20s) → page/load/expand(自己的 60s) ─┼─ 低内存阶段有界并行
   │                                                       │
   │                                                       ▼
   │                                      HEAVY_STAGE_WAIT（只计时、无失败时限）
   │                                                       │
   │                                                       ▼
   │                                           fair Semaphore(1) / Heavy = 1（固定）
   │                                                       │
   │                                                       ▼
   │                                    HEAVY_STAGE_WORK（自己的 60s）
   │                                                       │
   │  资源网络下载并发 = reviewResourceDownloadConcurrency（默认 8，范围 1～32）
   │                                                       │
   │  临时文件 → 压缩/资源库写入 → DOM 引用替换 → outerHTML → JSON decode
   │                                                       │
   └───────────────────────────────────────────────────────▼
                                  snapshot stream write（不属于 Heavy permit）
```

原则：

- 不因为某个重内存阶段危险，就把整个 REVIEW 执行器永久全局串行化。
- 页面加载、网络等待、DOM 展开等低内存阶段可以有界并行。
- 章节消费者、Capture Pipeline 与 Heavy 分别是固定的 `1 / 2 / 1`；唯一可配置的评论并发是资源网络下载并发，默认 `8`、范围 `1～32`。不得把资源下载设置错误用于章节消费者或 Capture Pipeline。
- `PAGE_EXECUTION`、`HEAVY_STAGE_WAIT`、`HEAVY_STAGE_WORK` 是三个不同边界：排队时间不等于执行时间，也不得扣减后续 Heavy 执行预算。
- 每条 Capture 的页面/Heavy 执行超时必须独立计时；超时看门狗不得依赖共享主线程 Looper，否则一个 WebView 卡顿会拖迟其它 Capture 的超时判定。
- `HEAVY_STAGE_WAIT` 只记录公平队列的等待耗时，不因前一条 Heavy 较慢而把后续 Capture 判失败。
- Heavy 执行超时时，必须取消活跃网络 Call、请求后台大对象 worker 停止；只有实际 worker 已退出且超时/取消 WebView 已丢弃后，才允许释放 permit 给下一条 Capture。
- 会同时持有完整 HTML、压缩 Bitmap / 大 `byte[]`、序列化结果的阶段必须单独做资源预算；评论图片不得再转成 Base64 字符串常驻 Java heap。
- pipeline concurrency 不能再与每章内部 concurrency 相乘形成不可控放大。
- 一条流水线完成一个大对象阶段后，应尽快解除对中间对象的引用。
- 能流式处理的读写优先流式处理。
- `evaluateJavascript()` 返回完整字符串这类 API 限制可以保留一个必要完整对象，但禁止在 Java/Kotlin 层继续制造多个无必要的完整副本。

### 8.2 大对象与流式处理

禁止让同一份大数据以多种完整形态同时长期驻留：

```text
raw HTML
   + decoded HTML
   + Regex result
   + Gson JSON String
   + 压缩 Bitmap / resource byte[]
```

推荐：

```text
DOM 内先去 script
      ↓
outerHTML
      ↓
直接 decode
      ↓
流式写 JSON / 文件
```

避免：

```text
outerHTML
  ↓
完整 String A
  ↓ Regex.replace
完整 String B
  ↓ Gson.toJson
完整 String C
  ↓ writeText
额外编码副本
```

### 8.3 BODY / MEDIA

- BODY 可以保留适合纯文本的并发策略，但不能绕过 Store/lease。
- AUDIO / VIDEO 可以按网络/播放器能力并发，但当前章节 bytes progress 必须统一回报 Store。
- 媒体执行器可以继续使用 ExoPlayer 或已有下载核心，终态只能通过 lease 回报。

### 8.4 限流与配置

允许：

- 有明确资源依据的并发上限。
- 可配置的 bounded concurrency。
- 独立 heavy-stage permit / memory budget。
- 通过日志观测等待、并发数、heap 和大对象大小。
- 对单个快照设置明确的资源预算，但预算命中必须产生可观测结果，不能静默伪装成“完整快照”。

禁止：

- 因 OOM 就直接删除整个并发能力。
- 无依据、无日志、无业务语义的静默截断。
- `take(N)`、累计字节阈值、单资源大小阈值命中后仍把快照当成“完整成功”而不留下明确状态/错误。
- 为“绝对安全”永久强制所有任务单线程。
- 新增并发设置却不核对 UI 默认值、`AppConfig` 默认值和实际读取点。


资源完整性契约：

```text
资源全部按要求写入资源库，且快照引用可离线解析
        -> snapshot COMPLETE -> 可记成功

资源预算命中 / 单资源过大 / 明确跳过
        -> 必须产生 RESOURCE_BUDGET_EXCEEDED / RESOURCE_PARTIAL 等显式诊断
        -> 当前没有 snapshot-level PARTIAL 业务状态时，不得把它伪装成“完整成功”
        -> 最小实现：该 button/snapshot 明确失败；若未来要允许部分快照，再单独引入 PARTIAL 语义
```

资源预算是防 OOM 的合法保护，但“有预算”和“静默丢资源”不是一回事。

### 8.5 TXT-ZIP 书籍归档 sidecar

普通文本与音频 TXT-ZIP 共用书籍级归档契约，但媒体章节仍由音频专用 Manifest 管理：

- `book_archive.json` 使用 `BookArchiveManifest`，声明唯一 `textFile` 与可选 `cover.image`；导出与导入都必须校验版本、路径和文件完整性。
- 封面属于导入后的书籍实体资源，恢复到 `BookArchive.persistentCoverFile(book)`，不放入可清理的正文缓存目录；删除归档书籍时由 `deletePersistentBookResources()` 一并清理。
- `cache_manifest.json` 只是缓存索引，不是 TXT-ZIP 归档 Manifest，也不是章节完成事实源。
- 音频 TXT-ZIP 另外使用 `audio_book.json` 和 `audio/`，章节集合及所有章节 sidecar 继续由同一个 `AudioOfflineState.isComplete` 选择集合驱动。

### 8.6 REVIEW 资源库、状态与导入导出

评论图片不写入快照 JSON 的 Base64；新快照统一使用资源库，不提供双存储模式设置：

```text
reviews/
├─ r_*.json                成功快照
├─ s_*.json                章节快照总数、失败数与更新时间
├─ resources.json           URL / hash / MIME / 大小索引
└─ rr_<sha256>.bin          按最终内容哈希命名的资源 blob
```

- 快照中的图片地址使用 `review-resource://<sha256>`；离线快照渲染必须由 WebView 拦截该 scheme 后打开资源库 blob。
- `resources.json` 只保存索引，图片 bytes 保存在 blob 文件；不同 URL 的相同最终内容必须复用同一 blob。
- `s_*.json` 独立于成功快照持久化。缓存管理按 `processedSnapshots / totalSnapshots` 显示；其中 `processedSnapshots = 成功快照数 + failedSnapshots`。失败数大于零时，单章和全部重试都必须通过 Coordinator 提交新任务。
- 导出必须按字节流带出 `r_*.json`、`s_*.json`、`resources.json` 与全部被索引的 `rr_*.bin`；导入必须恢复并校验资源库及章节状态，使 `review-resource://` 引用仍可离线读取。
- 任何包含 `r_*.json` 或 `s_*.json`、但缺少 `resources.json` 的本地缓存或导入包都是已废弃格式，必须直接报错；不得读取、导出、导入或从正文反推其状态。

#### REVIEW 快照资源闭包与离线 WebView 契约

一张 REVIEW 快照只有在最终 HTML 的本地资源闭包完整时才能持久化为成功。资源收集、写入资源库、DOM 引用替换与序列化必须针对同一份冻结 DOM 执行；不得在下载资源时继续从可变的活页面取 HTML，否则异步脚本新增或更换的资源会绕过本次资源清单。

- 开启头像或评论图片缓存时，对应 `<img>` 的最终 `src` 必须全部替换为 `review-resource://<sha256>`，且该 key 必须能在本书资源库中打开；不得保留 `http://` 或 `https://` 图片地址。
- `<img srcset>` 的每个候选地址必须在同一份冻结 DOM 中收集并替换；无法入库的 `http://`、`https://`、`blob:` 或相对地址必须让该 snapshot 明确失败，不得只替换 `src` 后留下可联网的候选。
- 外部样式表必须在最终快照中内联为 `<style>`；任何 `<link rel="stylesheet">` 都不得保留 `http://` 或 `https://` 的 `href`。
- CSS 内联后的 `url(...)` 与 `@import` 只能引用 `data:`、`review-resource://`、片段或 `about:blank`；其它外部/相对资源当前不支持递归入库，必须明确失败。外部样式表下载失败同样直接失败。
- 上述检查必须与最终序列化在冻结 DOM 内原子完成。发现缺失 blob、未替换的目标图片或外部样式表时，该 button/snapshot 必须明确失败并进入诊断，不能把残缺 HTML 写成成功快照。
- 允许用户关闭某类图片缓存；该开关明确关闭的图片不属于该类资源闭包。除此以外不得用“离线模式下反正不可见”掩盖应缓存资源的缺失。

离线渲染的网络策略只隔离真实网络资源，不隔离应用自己的本地资源 scheme：

- `http://`、`https://` 必须被离线策略阻止，并由 WebView 拦截层或 WebView 网络加载策略统一执行。
- `review-resource://` 必须到达 `WebViewClient.shouldInterceptRequest`，由书籍上下文解析资源 key 并流式打开 blob；不能被 `WebSettings.blockNetworkImage` 在拦截器之前误杀。
- 因此离线模式使用 `blockNetworkLoads = true` 隔离网络，同时保持 `blockNetworkImage = false`；不得把“禁止网络图片”当作离线快照的实现方式。
- WebViewPool 的实例在归还和重新获取时都必须恢复网络加载状态（`blockNetworkLoads = false`、`blockNetworkImage = false`）。每个页面初始化再显式应用自己的在线/离线策略，禁止上一个离线快照把状态泄漏给下一个页面。

### 8.7 隔离

- REVIEW 必须按 task / 章节隔离，不能按整本书误伤其它 task。
- reader 与批量 REVIEW 对同章发生重叠时必须复用/协调，不得互相 ownership 冲突后整批失败。
- 暂停/取消按 session/task 定向；只有“全部任务”命令才遍历活动 task。
- 任何并发实现都不得产生第二 Owner、第二 Store、第二通知源。

## 9. 修改验收清单

任何涉及下载/缓存的修改都必须确认：

### Owner / State / Lease

- 新的后台 Cache Task 入口只经过 `CacheCoordinator`；即时阅读正文加载明确属于阅读域，不混入 Cache Task。
- 新业务状态进入 `CacheTaskStore`。
- 执行器只通过 lease 回报。
- 旧 generation 不能写新 task。
- 没有新增 Owner、状态源、通知源或 Service 控制路径。

### Task / Unit / Lifecycle

- TEXT/BODY、AUDIO/MEDIA 与同 kind REVIEW 按章节 unit 表达依赖。
- reader REVIEW 能与已有活动 task 正确复用/协调。
- 暂停、恢复、取消走 Coordinator 命令。
- lifecycle/result 符合本标准，包括 `COMPLETED + FAILED`。
- Store 不接受带 unfinished unit 的成功收尾。

### Progress / Notification

- BODY 主进度条 = 已完成章节 / 总章节。
- AUDIO / VIDEO 主进度条 = 当前章节 bytes / total bytes。
- REVIEW 主进度条 = 当前章节 processedSnapshots / totalSnapshots，其中 processedSnapshots = 成功 + 失败。
- REVIEW 文字 = `快照：processedSnapshots/totalSnapshots  失败：failedSnapshots  x/y章`；失败数只属于当前 displayUnit。
- `x/y章` 与章节内部进度分开显示；`x` 必须来自 REVIEW 的 `SUCCEEDED unit count`，`y` 必须来自该 REVIEW task 自己的 unit 总数，不得借用前置 BODY / MEDIA task 的章节总数。
- denominator 未知时使用 indeterminate，不伪造百分比。
- progress 携带 lease 进入 Store；高频 progress 可不持久化，但必须由 Store 拥有/发布。
- REVIEW 并发时支持多个 unit progress，不允许用一个“最后更新章节”覆盖整个 task。
- 执行器不得直接更新通知，NotificationBridge 不得直接读取 ReviewSnapshotManager / AudioCacheTaskManager 的局部进度账本。
- session 仍有 REVIEW/MEDIA 活动 task 时不得错误显示整个缓存已完成。
- 多 task 并发时不得混合不同 task/unit 的进度分子分母。
- displayTask/displayUnit 选择稳定；progress tick 不得导致 MEDIA/REVIEW 之间来回跳。

### Pipeline / Memory

- REVIEW 页面流水线是有界并发，不是无脑乘法并发。
- 重内存阶段有独立资源预算。
- 不存在不必要的 raw/decoded/regex/json 多份完整大对象长期同时驻留。
- 能流式读写的路径使用流式处理。
- 限流有依据、有日志、可观测，不静默删功能。
- 资源数量/字节/单资源上限命中时必须显式记录并按资源完整性契约收敛，不能静默保存成完整成功。

### Logs / Diagnostics

- 请求、unit、终态、过期回报和持久化错误进入 AppLog。
- 高频 UNIT 日志可以采样，但失败、终态、异常不能被采样隐藏。
- BODY / REVIEW / MEDIA / STORE 的重操作有性能诊断边界。
- 性能日志包含必要的阶段、耗时、数据规模、active 和 heap 水位。
- 关键 START 可见，永久卡死不能因为 sampling 完全无日志。
- 日志不写完整大 payload，不制造新的性能问题。

### Recovery

- 进程恢复重新取得 generation。
- Service 不自行恢复任务。
- 旧运行态 progress 不跨 generation 复用。

## 标准形态

```text
一个任务 Owner
        │
        ▼
一个业务状态源
        │
        ├── Lifecycle / Result
        ├── Unit
        └── Progress
        │
        ▼
三类专业 Worker / Adapter
        │
        ├── BODY executor
        ├── REVIEW executor
        └── MEDIA executor
        │
        ▼
有界并发流水线 + 独立重内存预算
        │
        ▼
lease 回报 Store
        │
        ├── UI
        ├── Notification
        └── Lifecycle Log + Performance Diagnostics
```

核心验收原则：

```text
全库只能有一个缓存任务 Owner
全库只能有一个缓存业务状态来源
所有进度必须进入统一 Progress Contract
所有执行回报必须携带有效 lease
worker / executor 不得直接发最终通知
worker / executor 不得直接写最终任务状态
旧 generation 不得写入新 task
正文失败只阻断对应章节评论
评论失败不得污染正文结果
并发必须有界，重内存阶段必须有预算
所有缓存结果必须进入 AppLog
重操作必须具备性能可观测性
所有后台缓存任务入口必须走 CacheCoordinator；即时阅读正文加载属于阅读加载域，不在此约束内
```
