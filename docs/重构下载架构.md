# 下载/缓存当前实现架构

本文记录阅读 C **当前源码已经实现的**下载/缓存架构与行为。它是现状说明，不描述尚未实现的目标形态；后续调整前应先核对源码，再同步更新本文。

缓存域包含：

```text
TEXT + BODY          正文离线缓存
TEXT + REVIEW        评论快照缓存
AUDIO + MEDIA        音频缓存
VIDEO + MEDIA        视频缓存
```

导出是独立领域，不进入 `CacheCoordinator`。

---

## 1. 当前主任务链

离线缓存任务的主链如下：

```text
CacheActivity / CacheManage / MainViewModel / reader review
                         │
                         ▼
                 CacheCoordinator
                         │
                         ▼
                  CacheTaskStore
                         │
                         ▼
              CacheWorkerDispatcher
             ┌───────────┼───────────┐
             ▼           ▼           ▼
      TextBodyAdapter ReviewAdapter MediaAdapter
             │           │           │
             ▼           ▼           ▼
       CacheBook     ReviewSnapshot  AudioCacheTaskManager
       / Service      / Service      / ExoPlayer
             │           │           │
             └── lease + unit / finish 回报 ──┘
                         │
                         ▼
                  CacheTaskStore
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
             UI     Notification   AppLog
```

`CacheCoordinator` 是离线任务 session/task 的 Owner；`CacheTaskStore` 是
session、task、unit、生命周期、结果和 generation 的持久化状态来源。正文、评论和媒体
仍保留各自的执行器与局部运行态。

### 阅读页的直接正文路径

阅读页的即时加载与预读仍直接走：

```text
ReadBook -> CacheBook.download / downloadAwait -> WebBook / BookHelp
```

该路径不创建 `CacheCoordinator` task，也不带 cache lease。正文实际下载成功后，评论
请求会经 `ReviewWorkerAdapter.enqueueReaderReviewIfEnabled()` 进入
`CacheCoordinator.submitReaderReview()`；因此评论仍在 Coordinator 域内。

## 2. 职责和状态边界

### `CacheCoordinator`

负责：

- 接收并校验 `CacheRequest`。
- 创建 session/task，分派 worker。
- 处理暂停、恢复、取消及“全部任务”命令。
- 在 BODY task 结束后，为成功 unit 追加同一 session 的 REVIEW task。
- 复用同书同章的活动 reader REVIEW task。
- 在 Store 已接受终态后调用 `CacheNotificationBridge.finished()`。

Coordinator 不执行正文抓取、WebView、媒体下载或快照落盘。

### `CacheTaskStore`

Store 持久化并发布：

```text
CacheSnapshot
  └── CacheSessionState
        └── CacheTaskState
              └── CacheUnitState
```

其中包含 task/session 生命周期、结果、unit 状态、错误、更新时间和 generation。所有
`updateUnit()`、`finishTask()` 回报都会检查 lease 的 session、task 和 generation；过期
回报被拒绝并记录 `STALE_UPDATE_DROPPED`。

当前 `CacheSnapshot` **不包含**独立的 `CacheProgressState`。媒体字节进度和评论快照
进度均是执行器拥有的瞬时状态，不持久化到 Store。

### Worker / Adapter 与 Service

- `TextBodyWorkerAdapter` 把 task 翻译给 `CacheBook` / `CacheBookService`。
- `ReviewWorkerAdapter` 把章节登记到 `ReviewSnapshotManager`，由
  `ReviewCacheService` 消费。
- `MediaWorkerAdapter` 使用 `AudioCacheTaskManager` 和 ExoPlayer 缓存媒体。
- `CacheBookService` 与 `ReviewCacheService` 是 Android 前台执行宿主；前台通知都从
  `CacheNotificationBridge.foregroundNotification()` 取得基础通知。

Adapter/registry 维护运行期绑定、队列、Future 和局部结果，并通过 `CacheWorkerPort` 回报
unit/finish。它们不直接写 `CacheTaskStore` 的内部数据。

## 3. 请求、task、unit 与 lease

`CacheRequest` 当前支持的合法组合为：

```text
TEXT  + BODY
TEXT  + REVIEW
AUDIO + MEDIA
VIDEO + MEDIA
```

一个 task 的 units 均属于同一本书。BODY 完成后，Coordinator 从已 `SUCCEEDED` 的 BODY
units 生成 REVIEW task；BODY 失败不会把其他章节的 REVIEW 一并阻断。REVIEW 失败不会
修改 BODY unit 的结果。

`CacheWorkerLease` 包含：

```text
sessionId
taskId
generation
```

新 task 初始 generation 为 `0`。首次 acquire、reclaim、暂停后恢复都会使 Store 取得新的
generation；旧 generation 的 Store 回报会被丢弃。

### 当前 Unit 启动行为

当前三个 Adapter 在 task 启动时，都会遍历 task 中的 `PENDING` /
`REVIEW_ELIGIBLE` unit，并立即更新为 `RUNNING`：

```text
task RUNNING
  └── 所有可执行 unit 同时 RUNNING
```

之后底层执行器再逐章回报 `SUCCEEDED` 或 `FAILED`。因此 `RUNNING` 当前表示“已交给该
worker task”，而不是“该章正在被底层执行器实际下载”。大 task 启动会相应产生多次 Store
更新、Snapshot 发布与采样日志。

## 4. 生命周期、结果和恢复

当前生命周期使用：

```text
QUEUED -> RUNNING -> COMPLETED / FAILED
QUEUED -> FAILED
QUEUED -> CANCELLING -> CANCELLED
RUNNING -> PAUSING -> PAUSED -> RUNNING
RUNNING / PAUSING / PAUSED / INTERRUPTED -> CANCELLING -> CANCELLED
RUNNING（进程恢复）-> INTERRUPTED -> RUNNING
```

`CacheResult` 与生命周期分离：

```text
SUCCEEDED | PARTIAL | FAILED | CANCELLED
```

`finishTask()` 不接受 `CANCELLED`；取消使用 `beginCancel()` 和
`confirmCancelled()`。正常执行结束时，Store 根据 unit 成功/失败状态计算 task result；若
失败收尾时仍有未完成 unit，Store 将这些 unit 收敛为 `FAILED`。

`CacheTaskStore` 会把 `CacheSnapshot` 写入应用文件。进程恢复时：

```text
RUNNING    -> INTERRUPTED
PAUSING    -> PAUSED
CANCELLING -> CANCELLED
```

随后 dispatcher 重新扫描 `QUEUED` / `INTERRUPTED` task，获取/reclaim lease 后重新分派。
媒体字节、当前评论快照等执行期进度不跨进程恢复。

## 5. 当前进度和通知实现

`CacheNotificationBridge` 是唯一实际构造 Android 缓存通知的类。它由以下路径刷新：

```text
CacheTaskStore.publish -> CacheNotificationBridge.render(snapshot)
CacheCoordinator start / resume / finish -> CacheNotificationBridge
AudioCacheTaskManager state update -> CacheNotificationBridge.renderCurrent()
ReviewSnapshotManager snapshot progress update -> CacheNotificationBridge.renderCurrent()
```

后两条是执行器局部状态主动请求 Bridge 重渲染；它们不直接构造 Android notification。

当同时存在多个非终态 task 时，Bridge 为每个 task 计算展示信息，并选择
`updatedAt` 最新的一项作为当前通知内容；通知动作仍是暂停、恢复、取消全部活动 task。
终态时使用 session/task 已汇总的结果生成终态通知。

### BODY

```text
主进度条 = SUCCEEDED unit 数 / task unit 总数
文字       = 已完成章节数/总章节数章
```

示例：`2/5章`

### AUDIO / VIDEO

`AudioCacheTaskManager` 以 `bookUrl` 保存 `AudioCacheTaskState`。其中包含当前章节序号、
当前章节已缓存 bytes、当前章节总 bytes、总章节数和更新时间；进度状态最多约每 750ms
更新一次。

```text
主进度条 = currentChapterBytes / currentChapterTotalBytes
文字       = 当前章已下载大小 / 当前章总大小 当前章节序号/总章节数章
```

示例：`8.4MB / 60MB 2/5章`

当前 `2/5章` 是正在处理的章节序号，不是已完成章节数。未知媒体长度时显示 `?`，并使用
不确定进度条。

### REVIEW

`ReviewSnapshotManager` 使用内存中的 `notificationProgressByChapter` 保存每个
`session/task/generation/chapter` 的快照完成数和总数。快照成功写入
`ReviewSnapshotStore` 后，当前章节快照数递增；task 队列项结束时相应内存进度被清除。

```text
主进度条 = 当前章节 completedSnapshots / totalSnapshots
文字       = 快照：completedSnapshots/totalSnapshots  当前章节序号/总章节数章
```

示例：`快照：2/60  2/5章`

当前 `2/5章` 同样是展示的当前章节序号，不是已完成章节数。多个评论章节并行时，展示
最近更新的章节进度。

## 6. REVIEW 流水线、内存和资源处理

Review 按按钮抓取评论页。页面加载和展开阶段可以并行；实际活动页面流水线通过
`AppConfig.reviewCacheConcurrency` 统一限制在 `1..32`。每章的按钮 flow 使用同一配置，
但每个按钮处理都必须先取得全局 pipeline permit，避免“Service worker 数 × 每章按钮数”的
并发乘法。

重内存阶段使用单个公平的 `heavyStagePermits`：

```text
load / expand (可并行)
        │
        ▼
资源内联 + outerHTML + JSON decode（一次一条）
        │
        ▼
流式写入 ReviewSnapshotStore
```

当前快照处理包括：DOM 内删除 script、`JsonReader` 解码 JavaScript 字符串、Gson 直接写入
`Writer`，以及在读取统计字段时跳过大 HTML 字段。

资源内联当前仍有以下实现上限：

```text
每类最多 200 个资源
总内联体积超过约 30MB 后，后续资源不再内联
单个图片资源超过 8MB 时不内联
```

CSS 当前没有单独的 8MB 检查。资源请求失败、超限或被跳过不会使整个评论快照 task
失败；快照仍会继续序列化和落盘。

## 7. 生命周期日志和性能诊断

`AppLogCacheLogSink` 记录 session/task/unit 的结构化生命周期事件：

```text
SESSION_CREATED / SESSION_RECOVERED
TASK_QUEUED / TASK_STARTED / TASK_RECLAIMED
TASK_PAUSING / TASK_PAUSED / TASK_RESUMED
TASK_CANCELLING / TASK_CANCELLED / TASK_FINISHED
UNIT_UPDATED / UNIT_FAILED / UNIT_PROGRESS_SUMMARY
STALE_UPDATE_DROPPED
PERSISTENCE_LOAD_FAILED / PERSISTENCE_SAVE_FAILED
WORKER_DISPATCH_FAILED / REQUEST_ACCEPTED
```

`UNIT_UPDATED` 仅日志采样；Store 状态仍会完整更新。失败和终态不采样。

`CacheOperationDiagnostics` 记录 `STORE`、`BODY`、`REVIEW`、`MEDIA` 的重操作。日志字段
包含 domain、event、session、task、generation、chapter、大小/数量、阶段耗时、操作总耗时、
active、Java heap used/max/percent。关键的 capture、snapshot write 和 heavy-stage wait 起点
会强制写 START；完成阶段按自身耗时判断慢操作。
